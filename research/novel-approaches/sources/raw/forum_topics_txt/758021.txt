# Late post-processing cell never seems to affect the score in the hidden rerun — known differences vs. commit runs?
url: https://www.kaggle.com/competitions/name-that-llm/discussion/758021
author: vishu phalswal date: 2026-11-11 votes: {'canUpvote': True}
I have a notebook that scores 0.682. I added one extra cell at the end that refines the predictions after the main pipeline. It reads the pipeline’s saved logits, runs a GPU step in a subprocess (a compiled binary with its own bundled CUDA libraries), and then atomically replaces /kaggle/working/submission.parquet. If anything fails, it keeps the original file.

Offline, and in commit runs on a 4,000-row synthetic test set, the cell works and changes ~9% of labels. But every submission that should have used it scored exactly the same as the base (0.682). That suggests the cell always falls back in the hidden rerun. Since the hidden rerun shows no logs, I can’t see why.

Things I’d like to know from anyone who has run long or late GPU stages:

Time accounting: is the 9-hour limit measured from kernel start, or does it include queueing / environment setup? Has anyone seen the hidden rerun be noticeably slower than a commit run on the same data size?
Disk: is /tmp (or /kaggle/temp) the same size in the hidden rerun as in commits? My step writes several GB of intermediate files there.
Input read speed: first reads of large /kaggle/input files (100+ GB) are very slow for me in commits. Is it worse in the rerun?
Subprocesses / GPUs: any known differences in subprocess handling, LD_LIBRARY_PATH, or GPU/driver version between commit and rerun?
Debugging: has anyone found a reliable way to get diagnostic information out of a hidden run (other than encoding it into the score)?
